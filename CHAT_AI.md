# ИИ-консультант ПроРельс

GigaChat готовит ответы по каталогу и данным магазина. После подготовки черновик виден только менеджерам; сервер сохраняет срок отправки `sendAt = готовность + 7000 мс`. В админке `/admin/chats` показаны текст, таймер и кнопка «Отменить ответ и взять чат». Посетитель получает только отправленное сообщение с автором `AI`.

## Подключение

1. Обновить backend, выполнить `npx prisma migrate deploy` и `npx prisma generate`, собрать приложение. Миграция `20261113090000_chat_ai` добавляет очередь и автора `AI`. Существующие переписки остаются у менеджеров; новые разрешают ИИ, когда он настроен глобально.
2. Обновить frontend с поддержкой `AI` и панели черновиков. До этого оставить `CHAT_AI_ENABLED=false`.
3. Позже добавить **только в серверное окружение**, без коммита в Git:

   ```dotenv
   CHAT_AI_ENABLED=true
   GIGACHAT_AUTH_KEY=<ключ авторизации из кабинета GigaChat>
   GIGACHAT_SCOPE=GIGACHAT_API_PERS
   GIGACHAT_MODEL=GigaChat-2
   ```

   Scope зависит от аккаунта: для бизнеса `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP`. Значение ключа — готовая строка для `Authorization: Basic`, без самого префикса `Basic`. OAuth-токен обновляется автоматически. Перезапустить backend после изменения окружения.
4. При необходимости установить доверенный сертификат через `NODE_EXTRA_CA_CERTS`. Проверка TLS не отключается. Серверу нужен исходящий доступ к `ngw.devices.sberbank.ru:9443` и `api.giga.chat:443`.
5. Провести контрольную консультацию с реальной моделью: товар по артикулу, цена по запросу, адрес, сопутствующие товары, неизвестный товар, запрос менеджера. Проверить отмену черновика в админке до окончания таймера. Качество ответов и доступ аккаунта нельзя проверить без ключа.

Без флага или ключа запросов к GigaChat нет, обычный чат и уведомления работают. Отсутствие ключа видно в админке. Ошибка провайдера не превращается в сообщение клиенту: менеджер видит ошибку, может ответить сам либо повторить подготовку.

API: [авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api), [модель GigaChat 2 Lite](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-2-lite). Endpoint генерации: `https://api.giga.chat/v1/chat/completions`.

## Управление и защита от гонок

- «Взять чат на себя», отмена черновика, ручной ответ и завершение переписки выключают ИИ для этой переписки. «Включить ИИ» возвращает автоматические ответы; если последний вопрос ещё не отвечен, он ставится в очередь.
- Явные фразы вроде «Позовите менеджера» и «Хочу поговорить с человеком» также выключают ИИ. Уведомление о входящем сообщении идёт существующим почтовым механизмом; немедленный ответ человека не обещается.
- Новое сообщение посетителя заменяет старый черновик. Ответ старого запроса к модели отбрасывается по ревизии, даже если модель закончила после перехвата.
- Отмена и отправка блокируют одну строку переписки в PostgreSQL. Если отправка уже состоялась, отмена возвращает конфликт; UI не сообщает об успешной отмене задним числом.
- Очередь и таймер хранятся в PostgreSQL. После перезапуска готовые ответы отправляются по сохранённому сроку, зависшая генерация забирается после истечения аренды 90 секунд. Повторная обработка не создаёт второе сообщение.
- Не более двух одновременных запросов на процесс, задержка объединения входящих 800 мс, не более 40 отправленных ответов ИИ на переписку. Существующие лимиты входящих сохраняются.
- Черновики и ошибки не входят в историю посетителя, не рассылаются в его Socket.IO-комнату. Команды управления доступны только менеджерам. Уведомления по почте формируются только для сообщений посетителя.

Текущий Socket.IO работает в одном процессе, как и исходный чат. Для нескольких backend-реплик нужен общий Socket.IO adapter, иначе события между репликами не доставляются. База защищает от дублей, но не заменяет межпроцессную доставку событий. Путь WebSocket остаётся `/api/chat/socket.io`; настройки nginx не меняются.

## Контекст консультации

Системный текст: `src/chat/ai/chat-system-prompt.ts`. Здесь правятся описание магазина, адрес, телефоны, часы работы и правила консультации. Факты сверены с `ContactsPage.tsx`, `phones.ts`, `Requisites.tsx` и FAQ frontend ПроРельс.

`ChatContextService` добавляет актуальные названия из базы (до 1500 позиций / 90000 символов), детали до 8 релевантных товаров и до 8 кандидатов в сопутствующие. Поиск учитывает вопрос, артикул, ГОСТ и страницу обращения; ссылки собираются из slug категории/подкатегории/товара. В историю модели входят последние 20 сообщений, до 2000 символов каждое. Имя, контактные поля и токен сессии отдельно провайдеру не передаются. Текст самой переписки может содержать введённые посетителем контактные данные.

Промпт требует предлагать только уместные дополнения, не выдумывать цену или остаток и не подтверждать инженерную совместимость. Окончательный подбор, наличие, доставка и КП остаются у менеджера. Это инструкции модели, а не гарантия отсутствия её ошибок; для реальной модели нужен контроль после подключения ключа.

## Проверка

```sh
npm run test:regression
# Отдельная локальная PostgreSQL *_test, DATABASE_URL на 127.0.0.1:
node --test test/chat-ai.integration.cjs
```

Интеграционный тест поднимает настоящий NestJS + Socket.IO, использует настоящую PostgreSQL и подменяет только ответ провайдера через Nest testing override. Проверяет реальную семисекундную задержку, приватность, права, отмену возле срока, ручной перехват, устаревшую генерацию, ошибки, отсутствие ключа, повторные запросы и восстановление обработчика.

Для браузерной проверки запустить `node test/chat-ai-server.cjs` на loopback-порту 4191 и локальный frontend на 4173. Этот файл запускает **только тестовый провайдер**, не подключает GigaChat и не должен использоваться для рабочего сервера. Затем во frontend: `CHAT_TEST_AI=true PLAYWRIGHT_CHANNEL=chrome npx playwright test test/chat-ai.e2e.spec.ts`. После проверки остановить тестовый сервер. В приложении нет переключателя на фиктивные ответы.
