# Чат сайта и уведомления

Посетитель начинает переписку в виджете сайта, менеджер отвечает в `/admin/chats`. Все сообщения передаются по Socket.IO с транспортом **WebSocket**; HTTP используется только для создания гостевой сессии. Переписка сохраняется в PostgreSQL, список показывает непрочитанные сообщения и состояние чата. Новое сообщение повторно открывает завершённый чат.

## Установка

1. Установить зависимости (`npm ci`), применить миграции (`npx prisma migrate deploy`), сгенерировать клиент (`npx prisma generate`), собрать (`npm run build`) и перезапустить API. Dockerfile применяет миграции при старте, как прежде.
2. Обновить frontend из соответствующей ветки. Нужны `SITE_URL` и `API_SERVER_URL` на фронтенде; API требует `DATABASE_URL`, `JWT_SECRET`, `SITE_URL`. `CORS_ORIGIN` может содержать дополнительные разрешённые origins через запятую для WebSocket. Для штатного домена достаточно `SITE_URL=https://prorelsa.ru`.
3. Настроить доверенные IP/подсети прокси в `TRUST_PROXY`. Express не доверяет внешнему `X-Forwarded-For` по умолчанию. Если API стоит за nginx/контейнером frontend, без этой настройки лимит создания сессий будет общим для IP прокси. Пример значения — `127.0.0.1,::1,172.20.0.0/16`, но подсеть нужно заменить на фактическую доверенную сеть. Внешний прокси должен корректно устанавливать `X-Forwarded-For`.
4. Для писем используются существующие `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`. Адресат: `CHAT_NOTIFY_EMAIL`, иначе `NOTIFY_EMAIL`, иначе `SMTP_USER`. Письмо содержит имя, контакт, текст сообщения и ссылку на конкретную переписку в админке. Отвечать нужно из админки, ответы на письмо не импортируются.
5. Передать WebSocket Upgrade от внешнего прокси. Фронтенд поддерживает проброс этого маршрута на API и в dev, и в production. Если nginx направляет `/api/` сразу в backend, расположить отдельный маршрут ниже перед общим `/api/`:

```nginx
location /api/chat/socket.io/ {
    proxy_pass http://backend:3001;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 75s;
}
```

`backend:3001` — пример; использовать существующее имя и порт сервиса. Если весь трафик идёт на frontend, можно направить этот маршрут на frontend с теми же заголовками. См. [официальную документацию Socket.IO](https://socket.io/docs/v4/reverse-proxy/).

## Хранение и ограничения

- Гостевой секрет содержит 256 случайных бит, в БД хранится только SHA-256. Браузер хранит его в localStorage; срок доступа — 90 дней с начала сессии. Очистка данных браузера или другое устройство не восстанавливают анонимную переписку. В админке история остаётся.
- Менеджер использует существующий JWT и запись пользователя с ролью `admin`. Чужие переписки недоступны гостям. Авторизация проверяется для истории, отправки, чтения и завершения; секреты и служебные поля почты клиенту не выдаются.
- 4000 символов в сообщении; 30 новых сообщений посетителя в минуту; 10 новых сессий с IP в час. История выдаётся порциями по 50, список чатов — по 30. Пустые сессии в списке скрыты до первого сообщения.
- Повторная отправка с тем же `clientId` сохраняется один раз; подтверждение «Доставлено» означает запись в БД. Прочтение подтверждается открытым окном переписки. Черновик и идентификатор неподтверждённого сообщения сохраняются в sessionStorage.
- Письма ставятся в очередь вместе с записью сообщения. Обработчик проверяет очередь каждые 15 секунд, при ошибке увеличивает интервал до часа. Очередь переживает перезапуск API. Доставка SMTP выполняется как минимум один раз: если процесс оборвётся после успешного SMTP, но до записи подтверждения в БД, возможно повторное письмо. Повторных сообщений в чате при этом нет.
- Реализация рассчитана на **один процесс API**. Перед масштабированием нужны общий Socket.IO adapter и распределённые лимиты. Пример настройки нескольких узлов: [Socket.IO — multiple nodes](https://socket.io/docs/v4/using-multiple-nodes/).
- Вложения, голосовые сообщения и уведомления браузера в текущий объём не входят.

## Проверка

`npm run test:regression` — существующие проверки. `node --test test/chat.integration.cjs` — интеграция с запущенными локальными API и frontend. Требуется отдельная база с именем, оканчивающимся на `_test`, на `127.0.0.1`; тест не запускается с удалённой базой. Он использует локальный стандартный вход `admin/admin`, создаёт только свои чаты, удаляет их после проверки и подменяет SMTP памятью. Адреса по умолчанию: API `http://127.0.0.1:4191`, frontend `http://127.0.0.1:4173`; переопределяются через `CHAT_TEST_API_URL` и `CHAT_TEST_FRONTEND_URL`.

Перед публикацией проверить реальное письмо на настроенный адрес, заголовок Upgrade на внешнем прокси и права менеджера. Локальные тесты не отправляют писем на действующую почту.
